# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Airloom is a GNOME desktop app (developed on Fedora, distributed as a Flatpak) showing hyperlocal PurpleAir air-quality readings. It deliberately has **zero third-party dependencies**: Python stdlib + system PyGObject (GTK4, libadwaita, WebKitGTK 6.0, libnotify) on the backend, and hand-written vanilla JS/CSS on the frontend (no map library — OSM tile math is done manually in `app.js`). Keep it that way; don't add pip packages or JS dependencies.

## Commands

```bash
./run                                    # launch the app (or: make run)
make test                                # all unit tests (python3 -m unittest discover -s tests -v)
python3 -m unittest tests.test_aqi -v    # single test module
python3 -m unittest tests.test_aqi.TruncateTest.test_name  # single test
make check                               # tests + compileall + node --check and node --test (tests/js) — run before PRs
python3 scripts/test-ui-regression       # live cross-layer UI scenarios (needs a display; --list, --only NAME)
python3 scripts/make-screenshots         # regenerate packaging/screenshots/ in a private headless mutter
./scripts/build-flatpak.sh               # Flatpak bundle → dist/ (needs GNOME 50 runtime/SDK)
```

Python tests are pure stdlib `unittest` and run without GTK installed: the GTK-free modules are tested directly, and `app.py` adapter tests import it against `tests/gi_stub.py` when PyGObject is missing. JS tests (`tests/js/*.test.js`, `node --test`) cover `core.js` and `state.js`. `scripts/test-ui-regression` drives real WebKitGTK through isolated debug children with private config/cache, demo or fixture data, and a loopback geocoder (`test-heatmap` and `test-save-refresh` are smaller isolated debug-port checks); CI runs all three in the `webkit-ui` job under Xvfb, and locally they need a display (e.g. a private `mutter --headless` on its own `dbus-run-session`). The `keyboard-map` scenario sends real key presses through XTEST, so it needs an X11 display with the XTEST extension and `libXtst` (Xvfb, as in CI); without one it fails with "keyboard-map needs an X11 display with XTEST" (a Wayland-only headless mutter can run the other scenarios, e.g. with `--only`).

## Architecture

Two halves connected by a JSON message bridge:

- **Python shell**: `airloom/app.py` is the GTK adapter — `Adw.Application`, window, header bar, worker threads, GLib delivery, WebKit, and desktop notifications. State of record and decisions (refresh ordering, selection, favorites/hidden, preference transactions, alert eligibility, shutdown) live in the GTK-free `controller.py`, which `app.py` reports events to and acts on. Other GTK-free modules: `presentation.py` (display filtering, provenance, alert transitions — demo data and observations that fail the freshness rule never alert), `requests.py` (thread-safe request identity: only the newest token per context may publish), `geography.py` (canonical bounds, antimeridian splitting), and `validation.py` (JS-safe sensor IDs).
- **Web UI** (`airloom/resources/index.html` + `app.js` + `app.css`, with the pure `core.js` — geography, AQI bands, summary math — and `state.js` — navigation gates, keyed DOM reconciliation — loaded before it): rendered in an embedded `WebKit.WebView`; draws the map, lists, detail pane, and settings dialog from state pushed by Python.

**Freshness and provenance**: one freshness rule decides both alert eligibility and the Old badge. `models.is_fresh_observation(last_seen, now)` is true when the observation is at most `MAX_OBSERVATION_AGE` (2 h) old and at most `FUTURE_SKEW_TOLERANCE` (600 s) in the future, both inclusive; a missing time is not fresh. `AirloomCore.isFreshObservation` in `core.js` mirrors it, and cross-layer tests pin the boundaries, so change both together. Parsing applies the same skew tolerance (`models.plausible_observation_time`): an observation time more than 600 s in the future is discarded (`last_seen` becomes None) while the reading keeps its measured AQI and category, so it is never fresh, never alerts, and is badged Old (unless Demo or Stale takes precedence); times up to 600 s ahead are kept as clock skew. Likewise a response `time_stamp` more than 600 s ahead is never stored as a delta checkpoint. Invalid PM measurements (including JSON booleans) become unavailable. In the page, `AirloomCore.readingProvenance` applies one ordered rule per reading: Demo for synthetic data; otherwise Stale when a failed refresh fell back to cached data; otherwise Old when `isFreshObservation` fails (more than 2 h old, more than 600 s in the future, or unknown time); otherwise no badge, so fresh live and fresh in-interval cached readings are unbadged. It applies on every surface (popup, lists, sensor search results, detail card, marker names, announcements). The `#data-source` footer still shows Python's source string (e.g. "PurpleAir · cached 3 min ago") as delivery attribution for the batch, not as a per-reading badge.

**Bridge protocol** — the pair of functions to know:
- JS → Python: `bridge()` in `app.js` posts a JSON string to the `airloom` script-message handler; `_on_script_message` in `app.py` dispatches on `action` (`ready`, `refresh`, `select`, `favorite`, `hide`, `unhide`, `unhide-all`, `save-settings`, `view-changed`, `place-search`, `cancel-place-search`, `set-location-filter`, `reload-shell`). Note the quirk: JSC's `to_json()` wraps a posted string in an extra JSON encoding layer, so Python decodes twice (covered by `tests/test_bridge.py`).
- Python → JS: `_send(event, payload)` evaluates `window.Airloom.receive(event, payload)` in the webview; events are `config`, `sensors`, `loading`, `error`, `open-settings`, `location`, `view-name`, `places`, `trend`, `settings-save-result`, `shell-status`, `motion`, `pinch`, `restore-view`.
- Request identity: `save-settings` carries a `request_id`, and Preferences closes only on the `settings-save-result` with that id (errors stay inline). `places` results echo the search's `request_id` and `context` (`main` or `home`); `cancel-place-search` invalidates a context. `trend` events carry `sensor_id`, `request_id`, a `status` (`loading`/`loaded`/`unavailable`/`error`), and `reading_last_seen`. `shell-status` drives the page's recovery notice, whose Reload button sends `reload-shell`. After `reload-shell` or a renderer crash, Python ignores page messages until the new page's `ready`, invalidates the old page's place-search and view-label requests, and answers `ready` with `config` then `restore-view` `{lat, lon, zoom}` (the controller's current view; omitted before one exists) before refreshing.

**Threading**: network work runs on tracked non-daemon worker threads (`_start_worker`, refused once shutdown begins, drained at exit); results re-enter the GTK main loop via `GLib.idle_add` (`refresh()` → `_finish_refresh()`) and publish only if they are still current (`controller.accept_refresh`, `requests.is_current`). Cache reads and writes run on tracked workers (bounded trend workers, coalesced `_submit_coalesced` queues), and the main loop never touches SQLite (beyond opening the cache at startup and closing it once workers drain). Settings saves write, fsync, and rename the file on the main loop (a failure there raises and keeps the previous settings), but `store.py` confirms directory durability on its own `airloom-settings-sync` thread; its `on_durability_error` callback only `GLib.idle_add`s a warning toast (the save still succeeded and stays applied), and shutdown waits for it with one bounded `store.flush` (`SETTINGS_FLUSH_TIMEOUT_SECONDS`, 2 s). Never touch GTK/WebKit from a worker thread.

**Data flow**: with an API key, `purpleair.py` queries the PurpleAir REST API within `bounds_around()` the configured center; without one (or on any `PurpleAirError`), `demo.py` generates deterministic labeled demo sensors. `cache.py` sits between them: a SQLite cache (`~/.cache/airloom/cache.db`, GTK-free, thread-safe) of raw sensor field values plus fetched-region records. Area fetches are served from cache inside the `refresh_minutes` TTL, delta-polled via `modified_since` when stale (only changed rows are returned and billed), and fully fetched only for new regions; views wider than 200 km are capped (`cap_bounds`). Trend averages are not part of area fetches — they're fetched lazily per sensor on selection and cached. The header refresh button forces a poll (`refresh(force=True)`) but still delta-polls. On API failure, stale cached readings are shown (labeled stale) before demo data; a runtime cache failure degrades to uncached fetching rather than blanking readings. Demo data is never cached. Sensors with a PurpleAir `confidence` score (A/B channel agreement) below 90 are hidden at display time by default — `passes_confidence` in `models.py`, toggled by the `confidence_filter` preference; missing scores fail open. `cache.py`'s `SCHEMA_VERSION` (PRAGMA user_version) clears the whole cache on mismatch so stale rows without newly-requested fields never linger. `aqi.py` holds the US EPA 2024 PM2.5 breakpoints and the EPA corrections for PurpleAir data (`basis="CF1"`: Barkjohn et al. final equations, for current readings and indoor averages; `basis="ATM"`: the five-piece CF=ATM fit, for outdoor averages) — changes to AQI/data behavior need tests (per CONTRIBUTING.md). `store.py` persists config/favorites/alert state atomically to `~/.config/airloom/config.json` with mode 0600; the API key never leaves `public_config()` except as a masked hint.

`app.js` also has a browser-preview fallback (bottom of file): opening `index.html` in a plain browser renders demo data without the bridge, useful for UI iteration.

**Debug port**: launching with `AIRLOOM_DEBUG_SOCKET=/path/to.sock ./run` (or `scripts/debug-run`, which picks `$XDG_RUNTIME_DIR/airloom-debug.sock` by default and leaves other instances alone; a live socket at the same path is refused, not replaced) opens a local 0600 Unix socket — newline-delimited JSON, driven with `scripts/debug-client [--socket PATH] CMD [JSON_ARGS]` — so an agent can drive and inspect the running app. Commands: `ping`/`version` (version, git-describe build id, pid, `debug: true`), `eval` (JS in the webview), `pinch` (synthesize begin/change/end), `tap {x,y}` (synthetic pointerdown/pointerup/click via `window.Airloom.debugTap`), `search {query}` (`window.Airloom.debugSearch`), `key {key}` (`window.Airloom.debugKey`), `state` (single-round-trip snapshot from `window.Airloom.debugState`), `screenshot {path?}` (webview-only PNG via `WebView.get_snapshot`; base64 if no path), `resize {width,height}` (200–4000; also lowers the window's minimum size so narrow layouts can be probed), `notifications` (desktop notifications captured instead of shown), `quit`. `eval` also reaches `window.Airloom.debugZoomTo(zoom)` for deterministic zoom-level changes (e.g. to cross the heat-map threshold) — see `scripts/test-heatmap` for a full end-to-end example driven entirely over the debug port. Two debug-only seams, also in `debugport.py` and read only in debug mode: `AIRLOOM_DEBUG_FAKE_PURPLEAIR=/path/fixture.json` replaces the PurpleAir client with a fixture (`{"fail": bool, "rows": [...]}`, re-read per call), and `AIRLOOM_DEBUG_CAPTURE_NOTIFICATIONS=1` records notifications for the `notifications` command. See `airloom/debugport.py` — payload validation for every command except `eval`/`pinch` (`ping`/`version`/`state`/`quit`/`notifications`/`resize`/`tap`/`search`/`key`/`screenshot`) lives in its GTK-free `validate_command()` table, unit-tested in `tests/test_debugport.py` without a display. A debug launch runs with `Gio.ApplicationFlags.NON_UNIQUE` so it never just activates an already-running instance, and is visibly distinct: window title `"Airloom · DEBUG"` and a red header bar (`self.debug_mode` in `app.py`, decided once at startup) — the taskbar icon override is best-effort only since GNOME/Wayland ties it to the desktop entry. **Dev builds only**: the Flatpak manifest strips `airloom/debugport.py` from release bundles, `app.py` degrades gracefully when the module is absent, and `debug_mode` additionally refuses to activate inside a Flatpak sandbox (`/.flatpak-info`) — release artifacts stay inert even with the env var set. Trackpad pinch is intercepted as a capture-phase `Gtk.GestureZoom` in `app.py` (claimed before WebKitGTK's internal page-scale gesture can consume it) and forwarded over the bridge as `pinch` events; `window.visualViewport.scale` staying 1.0 is the probe that page-scale zoom stayed off.

## Releasing

Version lives in `airloom/__init__.py` and must match `CHANGELOG.md` and the AppStream release entry in `packaging/ai.stealthvision.Airloom.metainfo.xml`. Pushing a `vX.Y.Z` tag triggers the Flatpak workflow to build x86_64/aarch64 bundles and publish the GitHub release. See RELEASE.md, including its signing policy: protected upgrade verification keeps the previous install's own keyring and only redirects its URL (`--import-candidate-key` is development-only and refused for the production key), so a signing-key rotation fails the gate until a reviewed client migration exists. RELEASE.md also covers when a failed tag may be deleted and re-pushed.
