# Flatpak auto-update repository on GitHub Pages — design

Date: 2026-08-08
Status: approved

## Summary

Installed flatpaks currently come from standalone `.flatpak` bundles attached
to GitHub releases; they have no origin remote, so they never update. This
feature publishes every release to a signed flatpak (OSTree) repository
served by GitHub Pages at `https://ijbaird.github.io/airloom/`. Users add the
remote once (or install any post-change bundle, which embeds the origin);
after that, `flatpak update` and GNOME Software's automatic background
updates deliver every new release.

## Decisions already made

- **Approach**: self-hosted OSTree repo on GitHub Pages (not Flathub — can
  still be done later, independently).
- **Signing**: a new dedicated no-passphrase GPG key, generated locally on
  the developer's machine; private key stored only as the GitHub Actions
  secret `FLATPAK_GPG_PRIVATE_KEY` and in a local backup the developer keeps;
  public key committed to the repo and embedded in client files and bundles.
- **Pages**: enabled on `ijbaird/airloom` with the GitHub-Actions deployment
  source (`build_type: workflow`), via `gh api`.
- **Stateless publishing**: the Pages site is rebuilt from scratch on every
  release and always contains exactly one commit per arch — the latest.
  Old versions self-prune; clients update by pulling the new head (a full
  pull; the app payload is tiny, so cross-version static deltas are not
  worth keeping state for).
- **Bundle wiring (bonus)**: release bundles are built with
  `--repo-url=https://ijbaird.github.io/airloom/repo` plus the embedded GPG
  key, so installing a downloaded bundle configures the origin remote and
  auto-updates thereafter.

## Site layout (GitHub Pages)

```
/repo/                  OSTree repository (archive mode, GPG-signed summary + commits)
/airloom.flatpakrepo    remote description: Title, Url=…/repo, Homepage, GPGKey=<base64>
/airloom.flatpakref     one-click install: Name=ai.stealthvision.Airloom, Branch=stable,
                        Url=…/repo, RuntimeRepo=https://dl.flathub.org/repo/flathub.flatpakrepo,
                        IsRuntime=false, GPGKey=<base64>
/index.html             one short paragraph + the install command
```

The two client files are generated by the workflow (the GPG public key is
embedded at publish time from the committed key file, keeping one source of
truth), not hand-committed with a stale key inside.

## Workflow changes (`.github/workflows/flatpak.yml`)

**flatpak job (per arch, existing):**
- Keep the flathub `flatpak-builder` action for the build + cache; it already
  exports the app into a local OSTree repo directory (name per the pinned
  action's own docs/`action.yml` — verify during implementation).
- Add an explicit bundle step replacing reliance on the action's bundle
  output: `flatpak build-bundle <repo> Airloom-<arch>.flatpak
  ai.stealthvision.Airloom stable --repo-url=<pages>/repo
  --runtime-repo=https://dl.flathub.org/repo/flathub.flatpakrepo
  --gpg-keys=packaging/airloom-flatpak.gpg`.
- On tag builds (and workflow_dispatch), also upload the OSTree repo
  directory as a workflow artifact (`airloom-repo-<arch>`).

**publish-repo job (new; runs on `v*` tags and `workflow_dispatch`):**
- Runs after the per-arch builds in the same GNOME-50 container image (it
  has `flatpak`, `ostree`, `gpg`).
- Steps: download both repo artifacts → `ostree init --mode=archive` a
  publish repo → `ostree pull-local` each arch repo → import
  `FLATPAK_GPG_PRIVATE_KEY` into a throwaway GNUPGHOME → sign each ref's
  commit (`ostree gpg-sign`) → `flatpak build-update-repo
  --gpg-sign=<keyid> --gpg-homedir=<dir> --generate-static-deltas` →
  generate `airloom.flatpakrepo`, `airloom.flatpakref`, `index.html` →
  assemble the site directory → `actions/upload-pages-artifact` +
  `actions/deploy-pages` (job permissions `pages: write`, `id-token: write`;
  both actions SHA-pinned like every other action in this workflow).
- Idempotent: re-running republishes the same site.
- The GitHub-release job is untouched and independent; a Pages failure never
  blocks the release assets, and vice versa.

## Key management

- Generate once, locally: no-passphrase key, uid
  `Airloom Flatpak Repository <ijbaird@ijbaird.me>`, in a dedicated
  GNUPGHOME under `~/.airloom-flatpak-signing/` (never inside the git repo).
- `gh secret set FLATPAK_GPG_PRIVATE_KEY` with the armored private export.
- Commit the binary public key as `packaging/airloom-flatpak.gpg`.
- Leave `~/.airloom-flatpak-signing/README` telling the developer to back
  the directory up; a lost key means publishing under a new key and users
  re-adding the remote once.

## Client experience

- New install: `flatpak install --user
  https://ijbaird.github.io/airloom/airloom.flatpakref`; updates are then
  automatic (GNOME Software) or via `flatpak update`.
- Existing bundle installs: reinstall from any post-change bundle
  (`flatpak install --user --reinstall ./Airloom-x86_64.flatpak`) or
  one-time `flatpak remote-add --user airloom <pages>/airloom.flatpakrepo`
  followed by a reinstall from that remote.
- README.md and RELEASE.md document the install one-liner and the migration
  note; RELEASE.md's process gains "the tag push also publishes the update
  repo".

## Error handling

- Publish job hard-fails on: missing secret, GPG import/sign failure,
  `build-update-repo` failure, missing arch artifact — a partial/unsigned
  site must never deploy.
- `workflow_dispatch` on the publish path is the recovery tool: any failed
  or missed publish can be re-run from the same commit without re-tagging.
- Bundles keep working even if Pages is down (origin remote just fails to
  poll; flatpak treats it as a temporarily unreachable remote).

## Verification

1. Local static checks: workflow YAML parses; generated flatpakrepo/
   flatpakref templates match the documented format; `make check` stays
   green (nothing app-side changes).
2. After merge, a `workflow_dispatch` run publishes from main. Then, on this
   machine: `flatpak remote-add --user airloom-test <pages>/airloom.flatpakrepo`
   succeeds with GPG verification on, `flatpak remote-ls airloom-test`
   lists `ai.stealthvision.Airloom` for x86_64 and aarch64, and
   `flatpak install` + app launch works.
3. Bundle wiring: download the freshly built x86_64 bundle artifact, install
   it, and confirm the created origin remote points at the Pages repo URL
   with GPG verification enabled.
4. Full auto-update proof lands with the next real release: an installed
   older version sees the new one via `flatpak update`.
